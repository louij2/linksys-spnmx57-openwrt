# Phase 2b unresolved / validate-on-hardware checklist

38 items from the research pass. HW = needs the live board; DEC = design decision; BLD = build-verifiable.

1. [ ] Whether the QCA8386 exposes any register that distinguishes 2500 from 1000 at the switch-core MAC level: the ssdk shows it does NOT (MHT_PORT_SPEED_2500M == MHT_PORT_SPEED_1000M == 2, and _mht_port_speed_get has no 2500 case). If the mainline QCA8084/qca8k phylink integration needs the CPU port to report 2500, it must come from the fixed-link/phylink config and SerDes, not PORT_STATUS. Worth confirming against the 0930-0941 QCA8084 patches on the build host.
2. [ ] The HEADER_CTL (0x0098) special-ethertype value the QCA8386 expects when header mode is enabled is not pinned down here (TYPE_VAL[15:0]); mainline qca8k does not program it (length-style 2-byte QCA tag), so this only matters if a non-standard tagger is used. Needs the ssdk isisc header-init code or live readback to confirm the exact ethertype.
3. [ ] Exact PORT_STATE numeric value for 'forwarding' on QCA8386 (field is 3 bits [18:16]; ssdk enumerates disabled/blocking/listening/learning as 0-3, qca8k uses the same 0-3). The forwarding code (typically 3 or a HW-specific value) should be verified against isisc_port_ctrl.c stp state mapping.
4. [ ] The 32-bit page-split MDIO primitive itself (page written to pseudo-PHY 0x18 reg 0x0c) is not in this SSDK tree — it lives in the mii_bus sw_read/sw_write callback supplied by the kernel qca8k/platform-mdio glue (referenced via mdio_priv->sw_read at src/init/ssdk_plat.c:291-312). Confirm the exact page/split implementation against the qca8k kernel driver (or your RE notes) when wiring the DSA regmap.
5. [ ] The SPNMX57 SGMII+ link has TWO serdes that must agree at 2.5G: the IPQ5018 SoC-side uniphy (MAC1, driven by nss-dp/IPQ uniphy driver) and the QCA8386-side uniphy1 documented here. This analysis covers only the QCA8386 side; the SoC-side uniphy programming was not in scope and is handled by a separate driver.
6. [ ] Whether the new-stack port models the QCA8386 CPU serdes as a standalone phylink_pcs or folds it into the DSA driver's fixed-link CPU-port config is a design choice not decided by these sources; the register sequence is identical either way.
7. [ ] The analog-reset settle delay differs between sources (SSDK SGMII path mdelay(1) at mht_interface_ctrl.c:725 vs UQXGMII mdelay(10) at :449 vs mainline 10-11 ms). Recommend 10 ms for the port; not verifiable without hardware.
8. [ ] Reference/parent clocks for the nsscc: the six qca8k_uniphy0/1 rx/tx (incl. 312P5M) clocks have NO in-tree provider in v6.18 (not in the serdes patches, no PCS clock driver, no board .dts uses qca8084-nsscc). Need a live board + schematic to decide whether to model them as fixed-clock stubs (312.5M/125M) or add a PCS clock provider, and to confirm resulting link clocking.
9. [ ] The 50 MHz chip reference (DT_XO) source is not in any current DTS (qca-ssdk handled clocking) - confirm the QCA8386 reference oscillator on the SPNMX57 schematic and model it as a fixed-clock.
10. [ ] qcom,package-mode: board evidence (MAC_MODE_SGMII_PLUS, forced 2500) says SGMII+ switch mode => likely <1>, contradicting the binding-example default <0> (10G-QXGMII). Must be confirmed on hardware; determines whether xpcs-channel and the pcs-phy@6/xpcs-phy@7 subtree apply at all.
11. [ ] reset-gpios polarity (ACTIVE_LOW vs ACTIVE_HIGH) on gpio24 is a documented guess; confirm the package leaves reset on a real boot.
12. [ ] qcom,phy-addr-fixup last three entries (PCS0=5, PCS1-PCS=6, PCS1-XPCS=7) are binding defaults, not RE-confirmed for SPNMX57 - verify with a live MDIO scan (EPHYs 1-4 and the 0x10-0x1f window are confirmed).
13. [ ] nsscc reg=<0x18>: driver hardcodes the 0x10-0x1f access window and ignores mdiodev->addr, so any free address in that window works; confirm 0x18 is free on the live bus.
14. [ ] Whether the mainline nsscc + qca8084-package + PCS/XPCS path can actually drive the QCA8386 as a switch on this board (vs qca-ssdk) is unverified - no in-tree qca8k switch driver covers the QCA8386/MHT 8-port in v6.18; this DT describes the clock/PHY package only.
15. [ ] QCA8386 switch-core register MAP: qca8k's offsets (MASK_CTRL 0x000, PORT_STATUS 0x07c, ATU_DATA0 0x600, VTU_FUNC0 0x610, PORT_LOOKUP_CTRL 0x660+, GLOBAL_FW_CTRL0/1 0x620/0x624, REG_MIB 0x034, PORT_MIB_COUNTER 0x1000, TRUNK regs 0x700+, SGMII_CTRL 0x0e0, MAX_FRAME_SIZE 0x078) are QCA8337-family. Whether QCA8386 shares them (it is an HPPE/PPE-derived core in the vendor SSDK's hsl/mht tree) must be confirmed on hardware / against the QCA8386 datasheet before trusting FDB/VTU/lookup/MIB/mirror/LAG reuse. Only the ACCESS scheme (pseudo-PHY 0x10-0x1f + page@0x18/0x0c) is RE-confirmed.
16. [ ] The literal QCA8386 page-register offset 0x0c is a Phase-1 RE fact from the live bus; it is not present in the qca-ssdk snapshot at /tmp/ssdk (MHT reg access is routed through the external mdio driver's sw_read/sw_write callbacks, ssdk_plat.c:333-357). Confirm 0x0c against the qca-mdio bit-bang driver or a bus trace.
17. [ ] The QCA8386 PORT_STATUS speed field has no defined 2500 code in qca8k.h; the exact field position/value for forced 2.5G on the CPU port needs the QCA8386 register definition.
18. [ ] MAC/uniphy bring-up for the 2.5G SGMII+ CPU uplink (what mac_config/pcs_config must actually write) lives in the vendor SSDK src/hsl/mht/mht_interface_ctrl.c and the uniphy code; the exact DSA-side register sequence for SGMII_PLUS/2500 was not extracted here.
19. [ ] Tagging protocol for the CPU conduit: qca8k assumes DSA_TAG_PROTO_QCA with an eth-mgmt conduit. On the SPNMX57 the CPU link is a plain fixed 2.5G conduit; confirm whether QCA header tagging is enabled on port0 and whether get_tag_protocol/connect_tag_protocol should be kept.
20. [ ] Device-id location: confirm QCA8386 returns 0x17 at MASK_CTRL 0x000 bits 15:8 (read_switch_id assumes this).
21. [ ] MIB descriptor table (ar8327_mib[]) applicability and mib_count for QCA8386 not verified.
22. [ ] Whether the QCA8386 has an MDC-passthrough / MDIO-master enable bit that must be explicitly cleared in setup (qca8k clears QCA8K_MDIO_MASTER_EN in the dropped setup_mdio_bus external branch).
23. [ ] nsscc parent clocks have NO in-tree provider (hard blocker): qca8k_uniphy0_rx/tx, qca8k_uniphy1_rx/tx, qca8k_uniphy1_rx312p5m/tx312p5m, and the DT_XO 50MHz ref need fixed-clock stubs (312500000 / 125000000 / 50000000) or a PCS clock-provider before the nsscc probe can run; confirm link clocking on HW.
24. [ ] gpio24 reset ownership conflict (Sec3 vs Sec4): nsscc clock-controller@18 must be the SOLE reset-gpios claimant; the qca8386.c sw_probe reset_gpio block must be dropped and the switch DT node must NOT carry reset-gpios, else the second devm_gpiod_get gets -EBUSY. Validate package leaves reset and switch comes up after.
25. [ ] gpio24 polarity: GPIO_ACTIVE_LOW is an RE guess (vendor flag cell 0); if the package never leaves reset, try GPIO_ACTIVE_HIGH.
26. [ ] CPU-uplink serdes ownership conflict (Sec2 vs Sec3): decide whether the DSA CPU-port PCS or the qca8084-package driver (qcom,package-mode) configures uniphy1/SGMII_1; confirm they do not both drive it. No mainline precedent for DSA-switch + package-PHY + nsscc on one chip.
27. [ ] qcom,package-mode: board evidence (SGMII+ 2.5G switch mode) points to value 1 (QCA808X_PCS1_SGMII_MAC_PCS0_SGMII_MAC), not the binding default 0 (10G-QXGMII); confirm on HW.
28. [ ] Confirm QCA8386 reads device id 0x17 at MASK_CTRL 0x000 bits [15:8] so the driver binds.
29. [ ] Every reused QCA8337-family register offset (MIB base 0x1000/stride 0x100, ageing, MAX_FRAME_SIZE, port pad / SGMII_CTRL replacements, readable ranges) must be confirmed against the actual QCA8386 core map; compatibility is assumed, not proven for all.
30. [ ] regmap .max_register and .rd_table/readable_ranges must be set to the QCA8386 map bound, and extended to cover SERDES_CFG 0xC90F014 / the 0xC90Fxxx GCC block if the DSA driver reads SERDES_CFG at runtime for serdes discovery.
31. [ ] 2500 encoding (resolved in code per Sec1, verify on HW): PORT_STATUS SPEED field is NOT widened - write the 1000 code (value 2); the switch cannot report 2500, so pcs_get_state must read the serdes. Confirm 1000-code + serdes SGMII+/312.5MHz yields a real 2.5G link.
32. [ ] CPU tagging decision: does the fixed 2.5G CPU conduit use DSA_TAG_PROTO_QCA (and thus need HEADER_CTL 0x0098 TYPE_VAL/TYPE_LEN programming and get_tag_protocol)?
33. [ ] SerDes address discovery method: SSDK reads SERDES_CFG[9:5] at runtime vs mainline package DT pcs-phy/xpcs-phy fixed addresses - pick one for qca8386.c and confirm the resolved clause-45 address on the live bus.
34. [ ] Live MDIO scan: confirm nothing else answers at reg=0x18 and that qcom,phy-addr-fixup 5/6/7 (PCS0, PCS1-PCS, PCS1-XPCS) are correct.
35. [ ] SerDes bring-up timings: SGMII path uses mdelay(1) for the analog-reset pulse and adapter/function resets, but UQXGMII/mainline use 10ms and usleep_range(1000,1100). Validate whether 1ms suffices for stable high-temp lock or port the safer values.
36. [ ] Shared 0x18 page-register concurrency: DSA, nsscc, and package drivers all page to phy 0x18 reg 0x0c on &mdio1; confirm bus-mdio_lock bracketing serialises page-set + data across all three under concurrent traffic.
37. [ ] user-port port_set_status auto-follow: the qca8k port>0 && port<6 LINK_AUTO OR-in assumes internal PHYs; confirm correct behaviour for external QCA8084-fed user ports.
38. [ ] MDC-passthrough / MDIO-master bit: if the QCA8386 has an equivalent of QCA8K_MDIO_MASTER_EN, confirm it is cleared once (EPHYs are driven by the SoC MDIO, not the switch master).
