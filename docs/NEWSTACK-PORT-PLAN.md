# SPNMX57 → new OpenWrt DSA stack: port plan

Chosen 2026-09-05: port the QCA8386/QCA8084 to the mainline DSA ethernet stack
(stmmac/dwmac-ipq5018 + a NEW qca8386 DSA driver, kernel 6.18) on current OpenWrt
main, for real router mode (per-port WAN/LAN), per-port 2.5G, and an upstream-
quality release. The old qca-ssdk stack (shipped v0.4.0) can't do per-port cleanly.

## Feasibility
Feasible but LARGE, and all four lenses agree: the effort is dominated by writing a new QCA8386 (Manhattan/MHT) DSA driver from scratch. This is NOT a small qca8k delta. Mainline qca8k (drivers/net/dsa/qca/qca8k-8xxx.c) matches only qca8327/8328/8334/8337; the strings qca8386/qca8084/manhattan/mht appear nowhere in OpenWrt main or kernel 6.18. The QCA8386's 32-bit indirect MDIO protocol (page in phy 0x18 reg 0x0c; data pseudo-PHY 0x10|((addr>>5)&7)), its MHT-specific 952-line register map (include/hsl/mht/mht_reg.h), work-mode/EPHY_CFG init, switch-core clock tree, and switch-END SerDes/XPCS bring-up all diverge from qca8k. Qualcomm's own claim that the QCA8386 "can work with qca8k.c with supplement patches" is unbacked: no such DSA patch has ever been posted to lore/netdev/patchwork, and no WIP exists from georgemoussalem or quic_luoj.

What makes it feasible and bounds the risk: the ENTIRE SoC side is already mainline on the new stack and comes for free. gmac0/gmac1 are stmmac (dwmac-ipq5018.c, patch 0954); the 2.5G uplink PCS is uniphy0 (pcs-qca-uniphy.c, patches 0842/0951, CONFIG_PCS_QCA_UNIPHY=y); and critically our v0.4.0 "soft-reset all three uniphy lines so the forced 2.5G uplink comes up SGMII+ not SGMII" fix is now DECLARATIVE: patch 0723 sets GCC_UNIPHY_SOFT_RESET to bitmask 0x32 (SYS+RX+TX) and qca_uniphy_pcs_config_mode() asserts rst_soft on every 2500base-x mode change - triggered purely by phy-mode="2500base-x" on gmac1, no custom patch. Three more building blocks are upstream: the qca8084 quad-PHY driver (qualcommbe patches 0301-0312, needs backport to qualcommax), the PCS/XPCS 2500BASEX bits, and the qca8k-nsscc clock controller. The sibling SPNMX56 (ipq5018-spnmx56.dts) is a perfect SoC/DTS/board template on the identical new stack - only its switch subtree (qca8337) is inapplicable. So the SoC-to-UNIPHY path is a fill-in; the switch fabric is greenfield.

Note the standing business priority from HANDOVER.md: Luca wants 1G traffic end-to-end first (on the CURRENT qca-ssdk old stack, already at v0.2.0/v0.4.0), then an OpenWrt forum write-up + DTS share, THEN 2.5G. This DSA port is the 2.5G/router-mode/upstream endgame and sits AFTER that near-term 1G milestone; the qca-ssdk uniphy soft-reset win is independent of this port and should not be blocked on it.

## Phases
### Phase 1: Board boots on new stack, wifi only (switch dead)

**Work:** Cheapest real milestone: get current OpenWrt main building, flashing and booting on the SPNMX57 with wifi up, accepting NO working ethernet. Create target/linux/qualcommax/dts/ipq5018-spnmx57.dts: model 'Linksys SPNMX57', compatible 'linksys,spnmx57','qcom,ipq5018'; #include ipq5018.dtsi + ipq5018-ess.dtsi + ipq5018-mx-base.dtsi (mx-base matches the SPNMX57 vendor tree verbatim: wps gpio27, reset gpio28, PWM LEDs red/green/blue on pwm3/0/1, mdio1 pins mdc gpio36/mdio gpio37, qpic_nand+smem partitions+hw_mac_addr nvmem, uart, clocks). Copy the pcie0/ath11k QCN9074 tri-band wifi block from spnmx56, changing only qcom,ath11k-calibration-variant to 'Linksys-SPNMX57'. Leave &gmac0/&ge_phy DISABLED (57 wires neither to a socket). Leave the QCA8386 switch subtree OUT for now (no driver yet); optionally bring &gmac1 up as a fixed-link 2500base-x MAC with pcs-handle=<&uniphy0> and &uniphy0 okay @ UNIPHY_REFCLK_50MHZ purely to exercise the SoC path, but expect no traffic. Create ipq-wifi-linksys_spnmx57 caldata package. Edit image/ipq50xx.mk (Device/linksys_spnmx57 via Device/linksys_ipq50xx_mx_base, config@mp03.1, DEVICE_PACKAGES incl ath11k-firmware-ipq5018/kmod-ath11k-pci/ath11k-firmware-qcn9074/ipq-wifi-linksys_spnmx57), board.d/02_network, hotplug 11-ath11k-caldata, 05-wifi-migrate, init.d/bootcount, lib/upgrade/platform.sh - add a linksys,spnmx57 arm to each existing spnmx56 arm.

**Exit:** Image builds clean, flashes via the two-step sysupgrade flow (verify by a log line only the new build emits, per HANDOVER - dmesg right after flash shows the OLD boot), boots to a stable OpenWrt, both radios come up as APs, LEDs/buttons/failsafe work. Equivalent to the existing v0.1.0-wifi-only release but on the mainline stack. Ethernet explicitly not required.

### Phase 2: QCA8386 DSA driver skeleton: regmap, probe, chip-ID, clock/reset

**Work:** Stand up a NEW standalone DSA driver (drivers/net/dsa/qca/ - do NOT try to bolt onto qca8k; the indirect access + MHT register map make extension a false economy per every lens), added via a qualcommax patch plus a kmod-dsa-qca8386 entry in package/kernel/linux/modules/netdevices.mk. Implement the 32-bit indirect MDIO regmap bus (page select phy 0x18 reg 0x0c; 32-bit data via pseudo-PHY 0x10|((addr>>5)&7)) - port it from the qca-ssdk Rosetta stone at srv-openstack:/tmp/ssdk/.../src/init/ssdk_plat.c (qca_mii_reg_convert / qca_mii_raw_read/write) and include/hsl/mht/mht_reg.h. Implement probe + chip-ID read, package reset on gpio24, and the strap/clk fixups (phyaddr_fixup=0xc90f018, uniphyaddr_fixup=0xc90f014, mdio_clk_fixup). Bring up the switch-core + MAC0-5 clock tree: decide between enabling mainline nsscc-qca8k (CONFIG_IPQ_NSSCC_QCA8K, add DT node) vs doing it inside the driver from ssdk_mht_clk.c (switch core parented off UNIPHY1_TX312P5M at 312.5MHz) - this is a flagged open question. Add the DSA node to &mdio1 in the DTS (compatible 'qca,qca8386' NEW, pseudo-addr 17).

**Exit:** Driver probes on boot, reads and logs the correct QCA8386 chip/revision ID over the indirect MDIO path, switch core clock is running at 2.5G (verify against a known MIB or ID register that reads sanely, not all-ones/all-zeros - HANDOVER warns all-ones guards matter). No ports/traffic yet.

### Phase 3: CPU-port uplink live at SGMII+ 2.5G, single netdev passes traffic

**Work:** Bring up the SoC<->switch uplink end-to-end. SoC end is free: &gmac1 okay, pcs-handle=<&uniphy0>, phy-mode='2500base-x' (this fires patch 0723 + qca_uniphy_pcs_config_mode's mandatory 3-line soft reset = our v0.4.0 fix, declaratively). In the driver, do the SWITCH end the SoC side cannot reach: work_mode_init (WORK_MODE reg 0x10 = MHT_SWITCH_MODE), EPHY_CFG (0x00020c41 + clear the [21:20] calibration gate), and the switch-side SerDes SGMII+ bring-up over MMD to SRDS1 @ MDIO addr 6 / XPCS @ 7 (mht_interface_ctrl.c: mht_uniphy_calibration poll MMD1 CALIB4, mht_uniphy_xpcs_soft_reset MMD3 DIG_CTRL1 bit15, mht_uniphy_uqxgmii_function_reset). Wire the CPU port0: ethernet=<&gmac1>, fixed-link speed=2500 full-duplex. CRITICAL (HANDOVER): both ends MUST stay SGMII+/2.5G forced; dropping to SGMII/1G desyncs the switch-core clock and kills every front port. Pick and enable the DSA tag protocol (config shows NET_DSA_TAG_OOB=y; confirm whether QCA8386 uses OOB or a QCA-style tagger before wiring).

**Exit:** CPU port link is up at 2.5G full at BOTH ends (uniphy calibration-done polled, XPCS link up); the DSA master/conduit netdev passes frames to/from the switch CPU port (even before front ports work, a loopback or CPU-injected frame proves the datapath). This is old-stack v0.2.0 parity, re-achieved on the new stack.

### Phase 4: Four QCA8084 EPHYs up, per-port DSA netdevs appear

**Work:** Backport the qca8084 quad-PHY support from qualcommbe/patches-6.18/0301-0312 (extends drivers/net/phy/qcom/qca808x.c: QCA8084_PHY_ID 0x004dd180, config_init, package clocks/resets, package init, SerDes probe/init/speed, plus 0309 phy_package_remove_once) into target/linux/qualcommax/patches-6.18/ renumbered, and enable the symbol in config. Caveat: on IPQ9574 the QCA8084 sits DIRECTLY on the SoC over 10G-QXGMII; on the SPNMX57 the four EPHYs sit BEHIND the QCA8386 switch at MDIO 1-4, so the DSA driver must present them to DSA (port phy-handles) and own the ordering of package clock/reset vs PHY probe. Add the 4 downstream ports to the DSA node with phy-handle to the qca8084 PHY nodes (reg 1-4). Reuse the mainline pinctrl/mdio-master path so the switch-internal TLMM MDC/MDO reaches the EPHYs (mht pinctrl_init + mdio_master_init).

**Exit:** All four front-panel sockets link up when cabled (link/speed decode sane, up to 2.5G per the qca8084), each appears as its own DSA netdev (lan1..lan3, wan) named from the DTS port labels. Per-port up/down tracks the physical cable. This is the capability the old qca-ssdk single-'lan'-netdev never had.

### Phase 5: Router mode: VLAN/bridge/port ops, WAN=phy4 LAN=phy1-3 at 2.5G

**Work:** Implement the dsa_switch_ops that give router mode: port_bridge_join/leave, port_vlan_add/del/filtering, port_stp_state_set, port MTU/FDB, writing the QCA8386 lookup/VLAN/FORWARD_CTRL registers (semantics in mht_reg.h / the isisc switch-core layer; vendor reference ssdk_mht.c ssdk_portvlan_init). Set the confirmed physical mapping (HANDOVER hardware test: Internet socket = phy4, LAN1 = phy1): label port@1..3 lan1..lan3, port@4 wan. Add the board.d/02_network arm: ucidef_set_interfaces_lan_wan "lan1 lan2 lan3" "wan" (same shape as the spnmx56 arm). Verify 2.5G real throughput end-to-end (this was still open on the old stack - confirm dwmac-ipq5018 delivers 2.5G not 1G).

**Exit:** Default config boots as a router: WAN on the Internet socket (phy4) gets its own subnet/DHCP client, LAN = the other three sockets bridged with DHCP server, inter-VLAN isolation holds, and iperf3 across the uplink sustains meaningfully above 1G (target ~2.5G). Full router-mode parity with the product's intended function.

### Phase 6: Upstream-shaping, LEDs, docs, and release

**Work:** Polish for an upstream-quality release: split the driver into clean regmap/core/ops/serdes units matching netdev conventions, add dt-bindings YAML for 'qca,qca8386', per-port LED offload (CONFIG_NET_DSA_QCA8K_LEDS_SUPPORT analogue) if the QCA8386 supports it, MIB/ethtool stats, and phylink-correct fixed-link handling. Reconcile the nsscc-qca8k decision from Phase 2 into whatever is cleanest for submission. Write the OpenWrt forum write-up and publish the DTS (a forum user already asked, per HANDOVER). Prepare the netdev patch series (regmap+access, then chip support, then DSA ops) with the qca-ssdk provenance credited.

**Exit:** A tagged SPNMX57 new-stack release that boots, does 2.5G router mode with per-port netdevs, and is structured as a postable netdev/OpenWrt series; forum write-up + DTS published. Endgame reached.

## Reuse from the old-stack work
Substantial reuse, all as KNOWLEDGE re-expressed for DSA rather than code lifted wholesale. (1) The qca-ssdk vendor tree (srv-openstack:/tmp/ssdk/.../src/hsl/mht/, src/adpt/mht/, include/hsl/mht/mht_reg.h, src/hsl/phy/qca8084_phy.c, src/init/ssdk_plat.c, src/init/ssdk_mht_clk.c) is the Rosetta stone for the entire new DSA driver: the indirect 32-bit MDIO access, the 952-line MHT register map, work-mode/EPHY_CFG init, switch-core clock parenting, and the switch-END SerDes/XPCS calibration sequence all transfer directly. (2) Our v0.4.0 uniphy soft-reset insight is FULLY captured upstream and becomes free/declarative: patch 0723 (GCC_UNIPHY_SOFT_RESET bitmask 0x32 = SYS+RX+TX) + pcs-qca-uniphy.c's mandatory 3-line reset on 2500base-x mode change do exactly what our vendor adpt_mp_uniphy.c patch did, triggered by phy-mode=\"2500base-x\" - no custom patch needed. (3) HANDOVER.md hardware facts transfer verbatim: Internet socket=phy4/LAN1=phy1 mapping, gpio24 package reset, the strap fixups, the eth-50mhz refclk, the all-ones guards, and above all the hard constraint that the uplink MUST stay SGMII+ 2.5G at both ends or the switch-core clock desyncs and kills all ports. (4) The whole mx-base.dtsi board layer (buttons/LEDs/mdio1 pins/NAND/uart/clocks) and the ath11k wifi block are reused from the sibling spnmx56 essentially unchanged. What does NOT reuse: the old qca-ssdk single-lan-netdev datapath and swconfig model are discarded entirely - the point of this port is per-port DSA netdevs the old stack could never give.

## Open questions
Design/verification unknowns flagged by the lenses, ranked by how early they bite: (1) nsscc-qca8k applicability - NEW-STACK-TEMPLATE found CONFIG_IPQ_NSSCC_QCA8K explicitly 'not set' for ipq5018 and argues switch clocking is NOT via nsscc on this SoC (that's the IPQ9574/5332 story), while QCA8386-GAP argues enable it and consume its clocks/resets. Must resolve in Phase 2: enable nsscc-qca8k + DT node vs implement the clock tree inside the driver from ssdk_mht_clk.c, and confirm nsscc's register offsets/parent list match the QCA8386 (it was written for the standalone QCA8084 package). (2) Whether mainline drivers/net/phy/qcom/qca808x.c in 6.18 actually carries PHY ID 0x004dd180 AND the quad-package bring-up (per-PHY PLL, LDO on the middle two only, efuse trim gating) - could not read vanilla kernel source; if it does and honours the efuse the way vendor U-Boot does, the EPHYs should just work once clocked+reset; if not, Phase 4 grows. (3) The DSA tag protocol the QCA8386 needs behind dwmac-ipq5018 (OOB vs QCA-style) - NET_DSA_QCA8K's tagger did not appear in config-6.18, so how even the spnmx56 QCA8337 gets its tag enabled is unclear; confirm before Phase 3 driver design. (4) Whether the mainline uniphy PCS + a QCA8386 driver can jointly drive the true SGMII+ (3.125G line) mode the vendor uses, and reproduce/handle the HANDOVER's CPU-RX SGMII-vs-SGMII+ rate-mismatch on the new PCS path. (5) Real 2.5G throughput on dwmac-ipq5018 (caps at 1G vs delivers 2.5G) - still open from the old stack, validated in Phase 5. (6) Whether a distinct ipq-wifi board-2 caldata blob is needed for the 57 vs the 56, and the exact uniphy0 refclk mapping (56 uses UNIPHY_REFCLK_50MHZ; vendor SoC node also mentions internal 96MHz cmnblk) - confirm against patch 0842/0951 semantics.
